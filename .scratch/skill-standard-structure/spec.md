# 规范：dialogue-outline-generation 结构标准化与行为补全

Status: ready-for-agent

Type: spec

## Problem Statement

这个 skill 已经能跑，但作为一个要长期维护、并准备上架 skill 平台的产物，它现在的问题都出在**规范缺失**上，而不是功能缺失。

对使用这个 skill 的人（也就是把对话交给它整理的人）来说：

1. **产出形状不可预期。** 当一段对话里有几个互不相关的主题时，我到底会拿到什么——几个文件，还是一个文件里的几节？现有文档同时写着「明确无逻辑关联时另起一篇独立文档」和一组固定的三个文件名，两种说法互相矛盾。结果是每次执行可能长得不一样，我无法预期在目标目录下会看到什么。
2. **不知道什么会被记下来。** 我对话里夹杂的框架提醒、工具调用的机械返回、模型内部推理、hook 报错，是不是都会被原样归档？这既关系到隐私边界，也关系到归档文档还剩多少可读性。
3. **容易忘掉交接。** 长对话结束时我常常想不起来还要生成交接文档，事后再补就得重新整理一遍。
4. **这个 skill 无法校验、也无法上架。** 它的 frontmatter 不符合平台校验规则（`name` 字段带引号会直接导致校验失败），缺少平台要求的展示名与中英双语描述，模板文件放在一个非标准目录名里，而正文里自始至终没有引用过这些模板——也就是说 agent 实际上不会去用它们。
5. **分不清仓库里谁是给谁看的。** 拿到的是一个只有 `SKILL.md` + `templates/` 的裸目录，没有任何东西告诉我哪些文件是给 agent 读的、哪些是给人读的、哪些决策已经被锁定过。

## Solution

把仓库整理成一个符合官方规范的 skill 项目，并把上一轮 grilling 已经锁定的行为决策写进正式文档、写回 `SKILL.md`。

整理之后：

- 模板被真正引用，执行时会被加载，而不是躺在目录里没人碰；
- 归档产出的形状被写死——**主题是文件内部的二级标题，不产生独立文件**；**交接永远只有一份**；
- 哪些内容进流水、哪些作为框架噪音被剔除，有明确清单（内部推理不收录；hook 与工具报错保留摘要）；
- 整理结束时会主动问我要不要出交接文档；
- skill 可以通过平台校验并打包上架；
- 仓库里出现词汇表（`CONTEXT.md`）与四篇 ADR，说明每个设计取舍的理由，防止后人把刻意为之的设计当成疏漏"修掉"。

## User Stories

1. 作为使用本 skill 的人，我希望说"整理对话"就能触发归档，而不需要记住任何调用语法。
2. 作为使用本 skill 的人，我希望归档产出的目录形状是稳定可预期的，这样我下次能直接猜到文件在哪。
3. 作为使用本 skill 的人，我希望一段对话里的多个主题被如实切分，而不是被硬凑成一个叙事。
4. 作为使用本 skill 的人，我希望"主题"不会变成一堆小文件，因为我要的是可回溯的存档，不是碎纸机。
5. 作为使用本 skill 的人，我希望交接文档永远只有一份，因为下游 agent 需要一个**单一入口**，多份会逼它先做选择。
6. 作为使用本 skill 的人，我希望原始问答被逐字保留（含代码块），这样我能真的回溯当时的推理链。
7. 作为使用本 skill 的人，我希望框架噪音被剔除——系统提醒、连接器状态、时间戳注入这些不是我说的话，不该出现在我的存档里。
8. 作为使用本 skill 的人，我希望模型内部推理默认不收录，因为那是过程草稿而非我给出的内容。
9. 作为使用本 skill 的人，我希望 hook 失败与构建报错被保留为摘要，因为那往往正是这次对话的净结论所在。
10. 作为使用本 skill 的人，我希望净结论被单独提炼成一层，这样交接时不必把流水全文喂给下游。
11. 作为使用本 skill 的人，我希望净结论里能区分「决策/裁定」「约束/固定规则」「尚未解决/悬而未决」三类，这样我一眼看到哪些事还没落地。
12. 作为使用本 skill 的人，我希望可以指定归档到哪个目录，不指定时落到默认位置。
13. 作为使用本 skill 的人，我希望默认目录不存在时被自动创建；不可写时回退到一个我一定有权限的位置，而不是直接失败。
14. 作为使用本 skill 的人，我希望一次整理归档在一个以时间戳命名的独立批次目录里，这样多次整理不会互相覆盖。
15. 作为使用本 skill 的人，我希望重跑整理时旧批次原样保留，因为归档是历史快照，覆盖是不可逆的信息丢失。
16. 作为使用本 skill 的人，我希望落盘前先看到切分方案（有哪些主题、各自涵盖哪几轮、写到哪个路径），确认后再写，因为主题切分是主观判断，写错了要整轮重来。
17. 作为使用本 skill 的人，我希望主题很少（≤2 个）时免去这道确认，别让简单情况也卡一轮。
18. 作为使用本 skill 的人，我希望整理结束后被问一句"要不要生成交接文档"，因为我在长对话末尾最容易忘。
19. 作为使用本 skill 的人，我希望归档范围默认是整场对话，但我也能显式圈定范围（比如"只整理后半段"）。
20. 作为使用本 skill 的人，我希望目录时间戳取归档执行时刻，而不是让模型去猜对话首条消息的时间——猜错比不精确更糟。
21. 作为维护者，我希望 `name` 字段能通过平台校验（全小写连字符），不要再因为一个引号被拒。
22. 作为维护者，我希望 frontmatter 带上平台要求的展示名与中英双语描述，这样上架时不必回头重写一遍。
23. 作为维护者，我希望技能可以被模型自身后续修改（带上 `agent_created` 标记），否则将来连改都改不动。
24. 作为维护者，我希望打包时不会把 `.git`、`.DS_Store`、`__pycache__` 之类的垃圾带进去。
25. 作为维护者，我希望 `SKILL.md` 保持精简——只放触发条件、两个动作的定义和执行步骤，把长篇规则挪到按需加载的参考文档里，避免每次都占满上下文。
26. 作为维护者，我希望 `SKILL.md` 里提到的每一个资源路径都真实存在且被正确引用，别再出现"模板写了却没人读"。
27. 作为维护者，我希望有一份词汇表钉死「整理 / 交接 / 主题 / 流水 / 净结论 / 框架噪音 / 归档批次」这些词，并显式列出要避免的同义词，防止下游 agent 用语漂移。
28. 作为维护者，我希望词汇表里明确写着"主题不产生独立文件"，因为这正是本轮推翻旧决策的落点。
29. 作为维护者，我希望关键取舍被记成 ADR，让未来的人看到"没有独立目录""没有长度上限""交接不引用流水"时知道那是刻意的。
30. 作为维护者，我希望有一份面向人的 README，说明这个 skill 是什么、怎么安装、目录各部分的用途。
31. 作为维护者，我希望这个仓库的 issue 与 spec 有固定的存放约定，让 `to-spec`、`to-tickets`、`triage` 这些工程 skill 知道该往哪写。
32. 作为维护者，我希望改动完成后统一提交一次 git，而不是留下一串立刻被推翻的中间提交。
33. 作为接手这个仓库的下游 agent，我希望在动手前能先读到词汇表和 ADR，而不是靠猜这份文档为什么长这样。
34. 作为接手这个仓库的下游 agent，我希望被明确告知"主题切分是主观判断"，因此我的产出结构可以被校验，但我的切分选择不该被当成 bug。

## Implementation Decisions

### 目标仓库形态

采用官方推荐的三目录形态（`scripts/` / `references/` / `assets/`），并加上仓库级的文档层。这是本 spec 的核心交付物，用形状表达比散文精确：

```
dialogue-outline-generation/
├── SKILL.md                 # 瘦身：触发 / 两动作 / 执行步骤 / 资源引用
├── README.md                # 面向人：这是什么、如何安装、目录说明
├── CONTEXT.md               # 词汇表（single-context）
├── AGENTS.md                # 指向 docs/agents/* 的入口块
├── references/
│   ├── design.md            # 锁定决策 + 边界规则
│   └── output-format.md     # 产物规范
├── assets/
│   └── templates/
│       ├── 00_handoff.template.md
│       ├── 01_conclusions.template.md
│       └── 02_raw_log.template.md
├── docs/
│   ├── agents/              # issue-tracker / triage-labels / domain
│   └── adr/                 # 0001 - 0004
└── .scratch/                # 本地 markdown issue tracker
```

- **不创建 `scripts/`。** 归档是纯粹的模型动作，没有需要确定性复现的代码；建一个空目录只会制造噪音。将来真出现需要确定性执行的环节（例如结构校验脚本）再补，并同步修订本决策。
- **`templates/` 迁入 `assets/templates/`。** 官方把"用于产出的模板"归入 `assets/`，`templates/` 不是标准目录名。
- 不创建 `config/`、`examples/`：当前无对应需求。

### frontmatter 形态

技能元数据要满足平台校验（`name` 全小写连字符、SemVer 三段式版本、中英展示名与双语描述），并带模型可自改标记。描述字段一律用 YAML 折叠块 `>-`，避免裸值里出现英文冒号加空格导致解析报错。

字段清单：`name`（**不加引号**）、`display_name`、`display_name_en`、`description_zh`、`description_en`、`version: 1.0.0`、`description`（保留原有中文描述，措辞按词汇表口径微调）、`agent_created: true`。

### SKILL.md 的职责边界

`SKILL.md` 只保留：何时触发、两个动作（整理 / 交接）的定义、执行步骤、以及指向 `assets/templates/*` 与 `references/*` 的**显式引用**。以下内容一律移出正文：锁定决策、框架噪音清单、幂等与确认流程、路径回退规则——它们进 `references/design.md`。

这一条同时修掉现有缺陷：模板从未被正文引用，等于 agent 不会加载它们。

### 模板改版

- `02_raw_log.template.md`：主题标题统一为 `## 主题 N：<主题名>`；删掉「各自成篇」的措辞，改为「各自成主题节，不产生独立文件」。
- `01_conclusions.template.md`：结构升级——外层按主题分节，其下用三级标题承载三类净结论（决策/裁定、约束/固定规则、尚未解决）。**单主题时也保持同一结构**，不搞两种形态。
- `00_handoff.template.md`：保持唯一一份；新增「主题索引」一节（列出主题名，指向净结论中的对应分节）；明确"只引用净结论，不含流水全文"。

### 产物结构（对外契约）

```
<目标根目录>/dialogue-generation-file/
└── <归档批次: YYYYMMDD-HHMMSS>/
    ├── 00_handoff.md        # 仅当用户选择交接时产出
    ├── 01_conclusions.md
    └── 02_raw_log.md
```

- 路径优先级：用户显式指定 > 默认目录；默认目录不存在则创建；目标不可创建或不可写则回退。
- 归档批次取**执行时刻**；重跑产生新批次目录，旧批次不覆盖、不追加。
- 交接文档可能缺席（用户选择不产出），另两个文件必须齐备。

### 领域文档

- `CONTEXT.md` 采用 single-context 布局，**只放词汇**，不放实现细节。术语：整理（archive）、交接（handoff）、主题（topic）、流水（raw log）、净结论（conclusions）、框架噪音（framework noise）、归档批次（archive batch）。每项附 `_Avoid_` 同义词清单。
- 记四篇 ADR：主题在文件内分节而非独立目录；交接只引用净结论；不设字符硬长度兜底；流水与净结论分层存储。每篇一到三句，只记"决定了什么、为什么"。

### 工程 skill 的仓库配置

本仓库采用**本地 markdown** issue tracker：spec 与 issue 落在 `.scratch/<feature-slug>/` 下；工单一个文件一个票，编号从 `01` 起。triage 词汇沿用默认五个角色。域名文档为 single-context。

## Testing Decisions

**单一接缝原则。** 整个 skill 目录被当作**黑盒**，测试只断言它的外部行为，不碰实现细节（也就是不去断言 `SKILL.md` 的措辞、章节顺序或行数）。

这个仓库是 skill 仓库而非应用仓库，因此"外部行为"具体是两件事：

1. **产物结构契约**——给定一段固定的合成对话 fixture，执行一次整理，断言产出满足上文「产物结构」一节：批次目录存在、两个必需文件齐备、主题以二级标题分节、交接文档唯一且缺席时不影响其余产物。
2. **元数据合规**——`SKILL.md` 的 frontmatter 能被标准校验接受：`name` 符合全小写连字符、`version` 是合法 SemVer、五件套齐全且 YAML 可解析。

**什么算好测试。** 只测"换一种合理实现也应该通过"的性质：文件存在性、标题层级、字段可取。**不测**主题切分的具体结果——切分是模型的主观判断，把它写进断言等于给幻觉背书。也不在测试里复制 `SKILL.md` 的句子，否则文档一改测试就假红。

**哪些模块被测。** 只测两个接缝点，都不新增脚手架：

- 元数据合规复用**既有外部校验器**（skill-creator 自带的 `quick_validate` 脚本，以及 skill-packer 的打包校验），它们的通过/失败即为断言。
- 产物结构契约以一次端到端 dry-run 承载，产出目录本身是断言对象。

**不测什么。** 不测主题切分；不测噪音剔除的逐条判定结果（用固定 fixture 覆盖两个极端：含框架噪音的输入应被剔除、含 hook 报错与关键工具结果的输入应保留摘要）；不测模型输出的文字质量。

**先例。** 本仓库目前没有测试脚手架，上述两个接缝直接复用 ecosystem 里既有的校验脚本与一次人工 dry-run，属于"优先复用既有接缝"的取舍。若将来需要把 dry-run 自动化，新增的校验脚本应作为**接缝的补充**而非替代，并同步修订前面"不建 `scripts/`"的决策。

## Out of Scope

- 不新增任何脚本、配置或示例目录。
- 不做 git push（提交只在本机进行，推送另行确认）。
- 不把中文文档改写成英文；双语描述只覆盖 frontmatter 的平台必需字段。
- 不引入 multi-context 域文档结构（无 monorepo 信号）。
- 不实现归档产物的"追加到旧批次"能力——刻意不支持，避免半新半旧的产物。
- 不改动归档产物的三个固定文件名。
- 不为主题切分引入任何确定性算法或兜底规则。

## Further Notes

- **本 spec 推翻了一条旧决策。** 上一轮 grilling 曾锁定「明确无逻辑关联时另起一篇独立文档」；本 spec 改为「主题是文件内部的二级标题，不产生独立文件」。原因：交接文档需要一个单一入口，多份会迫使下游 agent 先做选择；同时"篇"这个词在现有模板里已经和"主题"混用，是歧义源头。这条改写已记入词汇表与 ADR-0001。
- **git 提交时机。** 全部改动完成后一次性提交；推送需要单独确认，因为它是外部可见动作。
- **远端可达性。** 远端指向 GitHub，但本机 `gh` CLI 未安装、且 `github.com` 的 git 操作受代理限制。这不阻塞本 spec（issue tracker 已选定为本地 markdown），但会影响将来是否改用 GitHub Issues。
- **词汇一致性要求。** 实施后，仓库内所有文档（含本 spec 提到的新文件）必须统一使用 `CONTEXT.md` 的术语，不得回退到 `_Avoid_` 里列出的同义词。
